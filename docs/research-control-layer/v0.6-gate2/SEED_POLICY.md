# Gate 2 Seed and Sample Policy

**Status:** DRAFT / PRE-REGISTRATION

## Planned design

- 11 seed conditions: 1 fixed reference position + 10 non-reference positions.
- 3 repeats per seed.
- Planned total: 33 atomic executions.

The planned count is not evidence of completed execution.

## R4 methodological closure

The 11 × 3 design is retained as a prospective methodological decision for bounded variability characterization. It is not claimed to be historically justified. The design limitations are binding: three repeats per seed provide limited within-seed precision, 11 seed-level units provide limited between-seed precision, and results do not generalize beyond the registered seed set.

The reference seed is a pre-specified fixed **registry position** used as a methodological anchor for within-protocol comparisons and stability monitoring. It is not a control condition, population baseline, or ground-truth reference and receives the same execution, measurement, and statistical treatment as every other seed.

R4 is closed. **Rule B is the canonical and pre-registered Seed Generation Rule for Gate 2.** Seed generation may proceed only under that deterministic rule; no execution is authorized by this decision.

## Canonical deterministic seed-generation rule

The following rule is frozen before any exact Gate-2 seed values are generated or registered.

### Domain and numeric representation

- Registry protocol identifier / domain: `ACAA-G2-v0.6-SEED-REGISTRY-v1`
- Generator input format: `domain | NONREF | index | counter`
- Hash: SHA-256 over the UTF-8 encoded input string.
- Candidate extraction: first four digest bytes interpreted as an unsigned big-endian 32-bit integer.
- Output domain: unsigned 32-bit integers.
- Rejected output values: `0` and `1`.
- Duplicate candidate values are rejected deterministically.
- No timestamp, wall-clock value, operating-system entropy, runtime RNG state, or execution-dependent input may influence generation.

### Critical index/value distinction

```text
index 0 ≠ seed value 0

index 0 = fixed reference-seed position
seed value 0 = rejected candidate output
seed value 1 = rejected candidate output
```

The reference seed is therefore generated by the same canonical deterministic procedure as every other registered seed. `index = 0` identifies its registry position; it does not prescribe a numeric seed value.

### Seed generation

Generate 11 seeds in fixed registry-index order:

```text
index 0  → REF-01
index 1  → NONREF-01
index 2  → NONREF-02
...
index 10 → NONREF-10
```

For each index, begin with `counter = 0` and increment the counter until the candidate is valid and unique:

```text
for index in 0..10:
    counter = 0
    while true:
        message = "ACAA-G2-v0.6-SEED-REGISTRY-v1|NONREF|" + index + "|" + counter
        digest = SHA-256(UTF-8(message))
        candidate = unsigned_big_endian_32bit(digest[0:4])

        if candidate not in {0, 1} and candidate is not already registered:
            register candidate at index
            break

        counter = counter + 1
```

The procedure is deterministic, domain-separated, reproducible across independent implementations, and independent of execution-time randomness. The counter is per index and advances only following rejection.

### Historical baseline separation

The frozen v0.5.0 baseline remains immutable and may be cited for provenance. Its commit hash is **not an input to the canonical Gate-2 seed generator**. Historical v0.5 seed values are not used as an exclusion criterion unless independently specified by a future versioned amendment.

### Ordering

Registry order is fixed as:

```text
REF-01
NONREF-01
NONREF-02
...
NONREF-10
```

This is registry order, not an execution-order randomization rule. If execution order is randomized later, the randomization algorithm, source seed, and resulting order must be separately pre-registered before execution.

## Frozen registry

Before protocol freeze, the exact seed values generated by the rule above must be committed in a machine-readable registry containing:

- seed ID;
- index;
- role (`REFERENCE` or `NON_REFERENCE`);
- numeric value;
- generation method and rule version;
- generation inputs/domain;
- registry creation timestamp;
- registry hash.

The creation timestamp is provenance metadata only and is not an input to seed generation.

After freeze, values cannot change without a versioned amendment and new freeze.

## Generation integrity requirements

The exact generated values must be independently recomputed from this rule before registry freeze. Independent verification must confirm:

1. exactly 11 unique values exist;
2. index `0` is labeled `REF-01`;
3. no generated value is `0` or `1`;
4. every value reproduces from the canonical SHA-256 rule;
5. registry ordering matches the prescribed index order;
6. the recorded registry hash matches the committed registry bytes.

Any mismatch blocks registry freeze and execution authorization.

## Execution order

Execution order must be recorded. If randomized, the randomization algorithm, source seed, and resulting order must be committed before the first execution.

## Repeats

Exactly three planned repeats are assigned to each seed. Failed runs are retained and are not silently replaced.

## Seed validity

A run with a seed not present in the frozen registry is `F-PROTOCOL` and is excluded from valid statistical analysis while remaining in provenance.

## Outliers

Outlier detection follows `OUTLIER_ANALYSIS.md`; flagged observations remain in primary analysis.
