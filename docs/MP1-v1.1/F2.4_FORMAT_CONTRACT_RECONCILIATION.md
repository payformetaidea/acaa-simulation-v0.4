# F2.4 — Format Contract Reconciliation

**Status:** EXECUTION AUTHORIZED / VALIDATOR FROZEN

## Purpose

Resolve whether `metadata.created_at` with `format: date-time` is a normative S1 assertion, an annotation, or an implementation-level validation policy.

## Frozen targets

- Validator baseline: `d1cef3768ccaa39525a0c23e1a9b94c3528a8995`
- Validator file: `infrastructure/schema-conformance/validate_s1.py`
- Schema at baseline: `infrastructure/schemas/invariant-registry.schema.json`
- Negative fixture: `infrastructure/schema-conformance/invalid/invariant-registry.invalid-date-time.json`
- Runtime investigation target: Ubuntu 24.04 / Python 3.12.3 / jsonschema 4.23.0

## Contract questions

1. Does the frozen schema declare the Format-Assertion vocabulary?
2. Does the schema merely contain the `format: date-time` annotation?
3. Does the project specification explicitly require syntactic `date-time` enforcement?
4. Is the invalid-date-time fixture therefore a valid Layer-1 structural-negative fixture?
5. Does the validator's use of `FormatChecker()` represent an explicit project policy beyond the schema contract?

## Normative reconciliation rule

For Draft 2020-12, `format` is annotation-only by default unless the Format-Assertion vocabulary is declared. Therefore the presence of `format: date-time` alone MUST NOT be interpreted as proof that a structurally invalid date-time value must fail JSON Schema validation.

If the project intends `date-time` to be an assertion, that intent must be made explicit in the contract (schema dialect/vocabulary or an independently normative S1 rule). A validator-specific option may implement that policy, but it cannot silently redefine the contract.

## Decision matrix

| Finding | Classification | Authorized consequence |
|---|---|---|
| Format-Assertion is declared and contract requires rejection | Validator/runtime defect if rejection does not occur | Controlled validator/runtime correction |
| Format-Assertion is not declared and no independent rule requires rejection | Fixture/oracle classification defect | Reclassify/remove Layer-1 expectation; preserve baseline validator |
| Format-Assertion is not declared but an independent normative S1 rule requires rejection | Validator policy must be reconciled with that rule | Controlled validator correction may be authorized after evidence |
| Contract sources disagree | Contract reconciliation blocker | No validator correction until authority is resolved |

## Evidence requirements

The F2.4 probe must record:

- exact target commit and file SHA-256 values;
- `$schema` and `$vocabulary` values;
- presence/absence of `format-assertion`;
- location and value of every `format` keyword relevant to `created_at`;
- actual validator construction;
- installed Python/jsonschema provenance;
- generic and Draft 2020-12 checker registry state;
- baseline fixture result;
- an explicit-vocabulary comparison schema result where supported;
- automatic classification based only on observed evidence.

No validator, schema, or fixture mutation is permitted by F2.4 itself.

## Governance boundary

F2.4 may authorize a later controlled correction only after the contract classification is evidence-backed. It does not approve S1, S1-A, S2, Gate-2, freeze, merge, or 33-run execution.
